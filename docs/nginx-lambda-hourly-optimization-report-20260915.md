# Nginx 整点 CPU 与 Lambda 调用优化报告

> **17:00 更新：** HTTP/2 与上游 keepalive 已在 14:16 生效。最新一小时及 16:00/17:00 对比见 [17:00 复查报告](kline-hourly-performance-20260915-1700.md)。下文保留 13:00 时形成的调查与原始方案，不能把其中“未启用”当作当前配置。

日期：2026-09-15 · 观测整点：13:00 Asia/Dubai（09:00 UTC）

## 结论摘要

- **整点集中建连是 Nginx CPU 高峰的主要来源。** 13:00 第一秒出现 383 次全新 TLS 握手和 384 次 bulk 响应；约 550ms 内 Nginx 消耗 463.31ms CPU，50% 的 CPU 样本调用栈包含握手。
- **优先验证 HTTP/2。** 383 次 ClientHello 全部声明支持 HTTP/2，Nginx 已有模块但未启用。如果同一个 Lambda 的两个 bulk 请求实际共享一条 HTTP/2 连接，可将该函数的握手数从两次降为一次。
- **分项实施和比较。** 先验证 HTTP/2 与 Lambda 内 Client 共享，再独立验证 Nginx → Java 的上游连接复用。具体 CPU 和延迟收益需要整点实测，不能从握手数直接推算。

## 自然整点：握手与收盘计算同时占用双核

2026-09-15 13:00 迪拜时间（09:00 UTC），对生产入口进行整点前 45 秒至后 30 秒的被动观测，没有发出诊断 HTTP 请求。第一秒同时完成 192 次 K 线 bulk 和 192 次资金费率 bulk 响应；连接数与请求数尚未逐条关联。

整点前 45 秒未观察到新 TLS 握手。整点第一秒的 383 条连接全部使用 TLS 1.3、AES-256-GCM 与 X25519；其中 378 条由客户端在同秒先发出关闭信号。它们支持“集中建立短连接”的判断，但不能仅凭这些数据认定客户端代码错误地销毁了连接池。

| 指标 | 观测值 | 范围 |
| --- | --- | --- |
| K 线 / 资金费率 bulk 响应 | 192 / 192 次 | 整点第一秒 |
| 新 TCP 连接 / TLS 握手 | 383 / 383 次 | 整点第一秒 |
| 客户端先关闭的新 TLS 连接 | 378 / 383 条 | 同一秒内 |
| 客户端声明支持 HTTP/2 | 383 / 383 次 | ClientHello ALPN |
| 客户端提供 PSK / 服务端恢复会话 | 0 / 0 次 | 383 次 TLS 1.3 握手 |
| Nginx CPU 时间 | 463.31 ms | 550.52 ms 窗口；两个 worker 累计 |
| Java CPU 时间 | 490 ms | 与 Nginx 相同窗口 |
| 整机 CPU 忙碌比例 | 90.8% | 与 Nginx 相同窗口；双核 |
| 包含 TLS 握手的 CPU 样本 | 46 / 92，50% | 与 Nginx 相同窗口 |
| K 线 bulk p99（沿用原口径） | 127 ms | 采集窗口内 193 次请求，全部 200 |
| 资金费率 bulk p99（沿用原口径） | 26 ms | 采集窗口内 193 次请求，全部 200 |

Nginx 在 550.52ms 窗口内累计执行 463.31ms，平均占用约 **0.842 个核，折合双核容量的 42.1%**。同窗口 Java 消耗 490ms CPU，整机忙碌比例为 90.8%。握手、TCP 收发及连接生命周期工作与 Java 收盘计算竞争同一台实例的 CPU。

本次采样中包含 `ngx_ssl_handshake` 的调用栈为 46/92。该比例已经包含调用栈内的内核执行，不能再与内核样本比例相加。Nginx worker 的这部分执行也不能归为 Java JIT。

**CPU 时间与请求耗时是两种指标。** Nginx 的 HTTP 请求计时不包含此前 TLS 握手全过程；Lambda 端到端耗时还包含启动、DNS、TCP 和 TLS 等阶段。因此本结论解释了 Nginx CPU 高峰，不能证明此前全部 bulk 尾延迟都由它单独造成。

## 连接方式对照证明了优化方向，但不代表 Lambda 的最终收益

12:24–12:26 迪拜时间，从实例外访问真实 HTTPS 入口。每轮 384 次 bulk 请求、16 并发，查询已完成的 K 线与已缓存的资金费率；两种模式各运行两轮。四轮返回体均为 767,834 字节，请求全部 HTTP 200。

| 指标 | 每请求新建 TLS | 复用 16 条已建立连接 |
| --- | --- | --- |
| 每轮 bulk 请求数 | 384 | 384 |
| 每轮返回体总字节数 | 767,834 | 767,834 |
| Nginx CPU：第一轮 | 690.38 ms | 143.20 ms |
| Nginx CPU：第二轮 | 654.08 ms | 119.25 ms |
| Nginx CPU：两轮均值 | 672.23 ms | 131.23 ms |

复用已建立连接后，Nginx 原始 CPU 均值下降 **80.5%**；估算扣除背景后下降约 80.9%。这说明重复建连成本显著。

复用组最初 16 次握手发生在计量窗口之外，新建组与复用组的运行时长也不同。生产自然批次的密钥交换组与对照客户端不同，独立 Lambda 也不能共同使用这 16 条连接。因此 **80.5% 不能作为线上 CPU 或 p99 的收益承诺**。

## Lambda 架构决定连接复用的范围

调用端是一组整点启动的 Lambda，这是用户确认的架构信息。每个执行环境拥有自己的进程内连接池；不同环境无法直接共享它。环境可能复用，但跨小时不能保证环境或 TCP 连接仍存活；整点被调用也不等于每次都冷启动。[AWS Lambda 最佳实践](https://docs.aws.amazon.com/lambda/latest/dg/best-practices.html)

如果每个函数并行调用 K 线和资金费率，即使同用一个 HTTP Client，HTTP/1.1 下仍可能为并发请求分别建连。HTTP/2 可通过同一连接上的多个流并行请求。[Nginx HTTP/2 文档](https://nginx.org/en/docs/http/ngx_http_v2_module.html)

“192 个函数 × 每个函数 2 次请求 ≈ 384 条连接”与本次数量吻合，但它仍是待核实的解释：本仓库没有 Lambda 调用端实现，也没有请求与函数调用的一一映射。即使打开 HTTP/2，独立 Client 或首次并发建连竞争仍可能产生多条连接。

## 按预期 ROI 排序的优化清单

下面是基于现有证据、改动范围和可验证性的工程排序，尚无足够数据计算精确的金额回报率。

| 顺序 | 优化方向 | 预期收益与条件 | 成本和风险 |
|---|---|---|---|
| 1 | **启用 HTTP/2，并确认 Lambda 内共享 Client** | 客户端已声明支持。若同一函数的两个请求实际共用一条连接，握手可从 2 次降为 1 次 | 服务端改动小；需要调用端验证协议协商、首次并发行为、错误与超时 |
| 2 | **Nginx → Java 开启 upstream keepalive** | 减少本机 TCP 建连和关闭；收益可独立验证 | 配置改动小；需检查连接失效、502 和连接资源占用；不减少入口 TLS 握手 |
| 3 | **提前启动同一次 Lambda 调用并预建连接** | 把入口握手移出整点，与 Java 收盘计算错开 | 调整触发流程、增加计费时长；必须使用同一次调用中的同一连接池等待整点 |
| 4 | **延长 Client 生命周期、验证 TLS ticket 复用** | 同一执行环境后续请求可能受益 | 跨小时效果不保证；自然批次未提供 PSK，仅加大服务端 cache 不能替客户端保存 ticket |
| 5 | **评估合并 K 线和资金费率接口** | HTTP/2 无法有效复用时，可用一次业务请求减少重复工作 | 需改两端接口，保留数据就绪、快照和部分失败语义；成本高于协议和连接配置 |

单纯增加 Nginx worker 数不会增加这台双核实例的 CPU 容量。bulk JSON 实测没有 gzip 编码，压缩不是本轮已识别的主要成本。优先处理有直接证据支持的连接开销。

## 分阶段实施方案

### 第一步：验证 HTTP/2 与同一次调用的连接共享

在现有 HTTPS `server` 块中增加 `http2 on;`，该语法适用于已核实的 Nginx 1.26.3。先执行配置检查，再通过平滑 reload 生效。客户端使用同一 Client，确认实际协商到 `h2`，并记录同一次 Lambda 的两个 bulk 是否复用同一连接。[HTTP/2 配置语法](https://nginx.org/en/docs/http/ngx_http_v2_module.html)

先以已完成、已缓存的只读数据验证 HTTP/1.1 和 HTTP/2 的响应语义、状态、超时及连接行为，再在自然整点观察。若已协商 `h2` 但握手数未下降，应继续检查 Client 实例数和首次并发建连，不能仅凭协议开启就宣告优化有效。

### 第二步：单独验证上游 keepalive

在后续独立批次，为 Nginx → Java 配置 upstream 连接池。以下为配置草案，`32` 是待验证的每 worker 空闲连接缓存起点，不是活动并发连接上限；它不表示经过测量的最优值。

```nginx
# http 上下文
upstream kline_backend {
    server localhost:1888;
    keepalive 32;
}

# 现有代理 location 内
proxy_pass http://kline_backend;
proxy_http_version 1.1;
proxy_set_header Connection "";
```

需确认该 location 的协议与现有路由要求相容。对于生产 1.26.3，显式配置上游 HTTP/1.1 和连接头，避免套用较新 Nginx 的默认值。[上游 keepalive 文档](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive)

### 第三步：必要时把建连移到整点前

如果协议与连接复用后的整点竞争仍明显，再评估提前启动同一次 Lambda 调用：启动 → 建立业务连接 → 等待整点 → 用同一连接池请求数据。另一次独立预热调用不能保证后续调用使用相同执行环境。该方案需要结合实际触发器精度和 Lambda 运行费用评估。

以上属于实施建议；本报告记录的证据来自优化前观测，尚无这组方案的生产变更后结果。

## 验收：同时看连接、CPU、正确性和端到端耗时

建议分阶段观察多个可比整点，记录每轮实际 Lambda 调用数和成功请求数；HTTP/2 与 upstream keepalive 分开变更，以便判断各自贡献。不要仅凭单个小时的 p99 下结论。

| 验收项 | 记录方法与判据 |
|---|---|
| 协议与前端连接 | 记录协商协议、连接标识、每连接请求数及 TLS 会话恢复；验证同一 Lambda 的请求是否实际共用连接 |
| 握手成本 | 统计整点第一秒新 TCP / 完整握手数，并按成功请求数归一化；若复用后未减少，应解释新增连接来自哪里 |
| Nginx 与 JVM CPU | 使用相同观测开销和时间边界，比较约 T 至 T+550ms 的进程累计 CPU，并同时记录整机忙碌和 JVM 就绪时序 |
| 用户实际延迟 | Lambda 记录 DNS、TCP、TLS、首字节及全部业务结果完成耗时；HTTP 日志与端到端延迟分别统计 |
| 数据正确性 | 相同闭合时间、币种集合与窗口下，响应内容、finalized / pending、错误和超时语义符合原有业务要求 |
| 稳定性与回滚 | 观察协议错误、连接重置、502/504、超时和资源占用；出现可复现回归时恢复本阶段配置并验证健康状态 |

“每函数两次握手降为一次”只有在每函数原本两条连接、实际合并为一条时成立；它不是 CPU 或 p99 减半的承诺。

## 口径、证据和结论边界

- **时间范围：** 自然观测计划覆盖 2026-09-15 13:00 前 45 秒至后 30 秒，时区为 Asia/Dubai（UTC+4）。CPU 窗口实际为 T−7.046 至 T+543.474ms。表中的 bulk p99 来自采集窗口内各 193 次请求，不是完整一小时的全部请求。
- **p99 口径：** 沿用既有脚本，对排序后样本取零基下标 `floor((n−1)×0.99)`，得到 K 线 127ms、资金费率 26ms。若采用最近秩 `ceil(n×0.99)−1`，则为 133ms、26ms。后续对照必须使用同一口径；样本量较小，尾部统计容易受少量请求影响。
- **观测开销：** 共捕获 12,361 个包，无内核丢包报告或 TLS 解析错误；目标整点完整覆盖，但采集末尾约一秒可能有缓冲中未写出的包。CPU 采样器同窗口消耗约 50ms CPU，perf/tcpdump 开销未单独隔离。
- **因果范围：** 被动抓包、CPU 栈和连接方式对照共同支持连接建立是 Nginx 高峰的主要来源；尚不能将每个请求关联到具体 TLS 连接，也不能把所有历史 bulk 尾延迟归因于此。
- **证据保留：** 仓库保留匿名协议元数据、CPU 汇总、符号化调用栈、计算脚本和文件哈希；原始 pcap 与 perf 栈内存留在实例，不嵌入报告。实际调用端代码及其冷启动、连接池记录尚未提供。

本报告复核了原始 CPU 计数增量、两种 p99 算法、对照均值及 ALPN 计数。报告可用于选择下一项实验；预期收益仍需以变更后的实际观测确认。
