# JIT 在线复查：第二个整点与当前编译活动

2026-09-14 17:21 UTC / 21:21 迪拜时间复查。结论是：**第二次整点有恢复，符合预热后改善的现象；当前 JIT 没有持续占满资源，但现有记录无法确认首次变慢由 JIT 引起。HTTP 在第二次整点仍明显慢于旧版。**

三个整点分钟均为 193 个 bulk POST，全部 HTTP 200，响应体大小分布接近。HTTP 请求耗时不等于整点后客户端收到数据的时刻；没有请求体或精确并发轨迹，不能视为严格同负载对照。

现货校时偏移依次为 -12、-62、-49ms，绝对 ready 值受校时影响。单调时钟记录的排队时长仍证明第二个整点的本地等待明显减少。合约偏移为 -5、-5、-3ms。17:00 的 T-5 至 T+10 秒内没有 GC 暂停；上次检查的 16:00 同样没有。

## 当前 JIT 的直接测量

在同一进程 PID `531654` 上，于 17:16:35–17:17:35 UTC 每 5 秒采集 `/proc/<pid>/task/<tid>/stat`，同时读取 13 次 `jstat -compiler -t`。

- 60 秒内，应用消耗 **6.33 CPU 秒**；两个 C1/C2 编译线程合计 **1.31 CPU 秒**，约占应用 CPU 的 20.7%、双核总容量的 **1.09%**。
- 编译计数增加 **167**，说明 JIT 仍在活动；编译累计耗时增加约 1.32 秒。
- 采样中的编译线程 ID 和启动时间保持一致，CPU 差值没有跨线程重建拼接。
- `Compiler.queue` 的 C1、C2 队列均为空；代码缓存剩余空间充足，`full_count=0`、`stopped_count=0`。没有看到代码缓存耗尽或持续编译积压。

编译累计耗时与 CPU 时间是不同口径。[JDK 对 CompilationMXBean 的说明](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/java/lang/management/CompilationMXBean.html#getTotalCompilationTime())将其定义为各编译线程累计的近似经过时间；此处 CPU 占用另由 Linux 线程 CPU ticks 计算。上述一分钟位于两个整点之间，**不能用于排除整点期间短时的 JIT 峰值**。

## 能判断到哪里

实例没有保留 16:00、17:00 两次整点的 JFR，也没有可回查的编译日志或本机历史编译指标库。当前 `JFR.check` 没有录制；VM 编译事件环形日志只有最近 20 条，覆盖进程 uptime 6891.655–6925.226 秒，已经晚于这两个整点。

因此，“第二次更快”支持存在某种预热因素，但不能区分 JIT、类加载、缓存状态、线程调度或请求变化。第二次 HTTP 中位数仍为 332ms、p99 仍为 821ms，现阶段也没有证据将全部额外等待归给首次 JIT。

要验证整点编译是否挤占工作线程，需要在同一整点窗口同步记录编译事件、编译线程 CPU、消息 ready/queue 与 HTTP 等待调用栈；目前没有这些历史采样，不把 JIT 当作已证实根因。

复查时健康为 UP，PID 保持不变，`NRestarts=0`。本次使用现有进程的诊断计数、事件日志和线程 CPU 数据。
