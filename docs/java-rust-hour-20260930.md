**Java / Rust 整点性能评估｜2026-09-30（UTC）**

整点收盘后，两边把刚收盘的 bar 收齐的时间相差几十毫秒以内；差距在收齐之后把数据交给调用方的阶段。

- 生产环境（Java 1.8.9 对 Rust 0.4.22，各自的 VPS）：200 个客户端的 bulk p99，Java 为 272–494 ms，Rust 为 117–145 ms。
- 同一台测试机、相同的回放负载：Java 能接住全部 392 个同时到达的 bulk，但成功请求的 p99 为 531–963 ms。Rust 成功请求的 p99 为 116–140 ms，但因为在途查询上限是 256，每小时有 136 个请求被直接拒绝（503）。只回放真实规模的 192 条生产请求链时，Rust 全部成功，完成时间约为 Java 的 1/4。
- 合并后的 Java master 与 1.8.9 交替运行时，CPU 和内存没有可测差异。
- 生产 1.8.10 修复了整点后约 10 ms 内拿到上一小时数据的问题。但 17:26 重启后，头三个整点车队明显变慢，第四个整点恢复；20:00 首 0.6 s 内 JIT 编译线程占 JVM CPU 37%。
- Java 重启后先跑一遍整点路径预热，测试波 p99 从 774 ms 降到约 565 ms，两次预热结果几乎相同；但整点第一秒 JIT 仍占 JVM CPU 约一半（第 4 节）。
- Rust 的两处硬上限改为有界排队后，392 个同时到达的 bulk 全部成功，p99 117–128 ms（第 5 节，未部署）。Rust 整点延迟约 85% 是在等币安发出收盘数据，自身处理只占 8–13 ms。

## 2. 同机同负载整点

一台与两台生产 VPS 同规格的东京测试机（2 vCPU Skylake、3.9 GB、Debian 13），每个整点只运行一个版本：

- 运行环境：JDK 二进制与生产相同（三个 sha256 一致），JVM 参数与生产相同；Rust 二进制和配置字节相同。nginx/TLS 站点对所有版本相同，只切换上游端口和日志路径。
- 时间线：整点前 53 分钟重启并从本机快照恢复，整点前 44 分钟开始回放 2026-09-30 06:15–07:05 的生产请求，扫描器和 exchangeInfo 按原顺序闭环发送。
- 整点负载：T+20 ms 同时放行 192 条资金费率 → bulk 请求链（每链 3 币）和 200 个 5 币测试 bulk。

**Rust 的在途上限。** Rust 用一张表合并相同的在途 bulk 查询，表里最多 256 个不同 key（`crates/kline-service/src/cache.rs:101`），满了就返回 503 -1008 `Response capacity exceeded`。整点时每个 closed_only key 都要在表里等到收盘确认，所以 392 个不同 key 同时到达时，超出的 136 个被直接拒绝，拒绝的 p99 为 20–29 ms。请求链的 bulk 要等资金费率那一步返回后才发出，这时表已经被测试波占满，所以请求链的失败率达到 63–66%。按当前车队规模（192）不会触发，但余量只有 64。

**解读边界：**
- **到达更集中**：回放把所有请求压在同一时刻放行，比生产上的实际到达更集中，两边的绝对值都比生产高。
- **成功率不同**：只算成功请求时，Rust 完成的工作量比 Java 少，“最后一个成功响应”不等于服务完全部请求所需的时间。
- **Java 的冷 JIT**：整点路径在每次重启后都是冷的，这一项会抬高 Java 的整点延迟，见第 4 节。

## 5. Rust 在途上限改为排队

第 2 节的拒绝来自两处硬上限，满了都立即返回 503 -1008：

- 不同在途 bulk key 最多 256 个（`crates/kline-service/src/cache.rs:101`）。
- 每个路由组最多同时处理 512 个请求（`crates/kline-service/src/http.rs:64`、`crates/kline-market/src/http.rs:60`）。

改动在 kline-proxy-rs 中完成，未部署、未提交（该目录不是 git 仓库），补丁见 kline-proxy-rs 的 `research/admission-queue-20261001/admission.patch`：

- 两处都改为有界先进先出排队，名额不变（256 / 512）。队列默认 4096，最长等待默认等于 `final_wait_ms`（8 s），超出才返回 503 -1008。截止时间严格，过期才轮到的名额交还下一个排队者。
- bulk 等待在途名额与 HTTP 排队共用一个预算，从请求到达路由组开始计。ticker 查询的 HTTP 排队不超过它自己的 5 秒总预算。
- `/health*`、`/actuator*`、`/metrics` 不排队，满载时探活和指标采集照常响应。
- `/metrics` 增加排队、拒绝计数和当前排队数。
- 修复原有的在途表清理竞态。原代码在最后一个持有者释放时，用 `Arc::strong_count == 2` 判断自己是否最后一个（同文件第 49 行）。两个持有者并发释放时可能互相看到对方仍持有，都不删除，条目就永久留在表里并占一个名额；整点 key 含边界时间，之后不会再被请求，名额收不回来，累计到 256 后所有新 key 都会被拒绝。现改为在锁内计数持有者。这是代码推导出的缺陷，没有证据表明生产上发生过。
- 验证：改动完成时 workspace 测试 235 个全部通过，主要修复都做了变异检查。Codex 多轮复核，最后一轮只剩文档措辞，已改。

同机复测：

| 392 个 bulk 同时到达 | Rust 0.4.22（第 2 节中位数） | 排队版初版 @02:00 | 排队版 @06:00 |
|---|---:|---:|---:|
| 成功：测试波 / 请求链 | 189 / 67 | 200 / 192 | 200 / 192 |
| 测试波 p99（仅成功） | 125 ms | 128 ms | 117 ms |
| 最后一个成功响应 | T+147 | T+150 | T+140 |
| 首秒应用 CPU | 0.23 s | 0.18 s | 0.20 s |
| 拒绝 | 136 / 整点 | 0 | 0 |

02:00 是第一版排队实现；06:00 的构建已含严格截止、共用预算和管理路由直通，之后的修改只涉及 ticker 排队上限、测试和文档。

**Rust 整点耗时的去向。**

| 阶段 | 时刻或耗时 | 依据 |
|---|---|---|
| 币安生成合约收盘消息 | 约 T+100–110 ms，整批同一时刻 | 本机订阅公开流，记录消息自带的事件时间 E |
| 收盘到达服务器 | 中位多为 T+116–136（00/06/12/18 点约 T+37–52），最后 T+120–146 | 生产 Rust 最近 24 个整点的 `/health/diagnostics` |
| 最后一个响应生成 | 最后到达后 8–10 ms（生产 200 个请求），13 ms（测试机 392 个） | `/health/performance` |
| nginx/TLS 与网络 | 3–9 ms | 客户端最后完成时间减应用最后完成时间（06:00 / 02:00） |

- 生产订阅的 `continuousKline` 是最快的收盘来源。2026-10-01 04:00，527 个合约的 `continuousKline_1h` 收盘全部在 T+108 ms 发出；同一批合约的普通 `@kline_1h` 中位在 T+464 ms，最晚 T+3,002 ms。
- 每条连接的流数不影响到达时间。测试机上 200 个合约的 1 分钟收盘，用 1×200、4×50、8×25 三种连接布局成对比较 30 分钟，最后一条到达的中位数分别为 122.0、122.7、122.7 ms，均没有超过 50 ms 的掉队。本机跨境链路上拆小连接反而更差：10 分钟中 6 分钟出现 200–320 ms 的停顿，形态符合 TCP 超时重传（推断）。
- Rust 自身的十几毫秒，主要是收盘整批到达后约 30 ms CPU 的响应构建排在 2 个构建线程上逐个消化。整点后第一秒应用 CPU 约 0.2 s，只占 2 个核的约 10%。
- 因此整点延迟约 85% 是在等币安，再优化 Rust 收益很小。同期在 Rust 中另做了 WebSocket 建连节流（每 5 分钟最多 150 次、跨重启计数），只为降低被封 IP 的风险，与速度无关；补丁见 kline-proxy-rs 的 `research/admission-queue-20261001/connect-pacing.patch`，测量脚本和数据见其 `research/ws-layout-20261001/`。

## 7. 方法边界与独立审计

数据和分析由 Codex（gpt-6-astra，只读）独立复算：同机 9 个整点的成功延迟、就绪时间、首秒 CPU、稳态 CPU/RSS，以及空闲测量全部一致。复算发现一处错误：第 1 节最后一个响应原先从 T+20 ms 起算，已改为从整点起算，四个整点各加 20 ms。

审计的主要保留意见：
- **成功过滤**：只算成功请求，不能抵消 Rust 和 Java 完成工作量的差异。
- **到达时间是合成的**：生产日志只有完成秒，回放把请求均匀铺开并闭环发送；Java 回放中的扫描器在整点首分钟落后计划 391–952 ms，Rust 约 1 ms。
- **各小时负载不同**：行情和资金费率数据随小时变化，拉丁方只平衡了顺序。
- **就绪口径与时钟**：两边就绪统计口径和交易所时钟估计方法不同，没有跨主机时钟误差界。
- **冷启动与回退**：生产 1.8.10 的冷启动与回退无法从被动数据中区分。

审计原文与复算表见 [审计记录](../research/java-rust-hour-20260930/audit/)。
